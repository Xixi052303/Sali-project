# GDD 分层结构

只在创建、整理或审查 GDD 时读取本文件。GDD 应记录已确认设计和可追溯状态，不把灵感清单包装成定稿。

## 文档层级

1. **产品摘要**：目标玩家、体验承诺、差异点、平台、视角和版本范围。
2. **设计支柱**：每项支柱包含含义、正例、反例和验证方式。
3. **核心循环**：观察、决策、行动、反馈、调整，以及局内与局外的衔接。
4. **系统规格**：输入、状态、规则、输出、反馈、失败条件、依赖和边界。
5. **内容框架**：塔、敌人、建筑、菜谱、谜题、地图和叙事内容的模板与预算。
6. **经济成长**：货币、产消、成长、奖励周期、难度目标和防滥用规则。
7. **关卡教学**：知识引入顺序、关卡压力、提示、失败反馈和难度递进。
8. **技术交接**：数据字段、事件、状态变化、验收样例和待工程评估项。
9. **验证计划**：原型问题、测试方法、成功阈值、失败后的处理。
10. **决策记录**：确认项、候选项、未决冲突、废弃项、负责人和来源。

## 推荐的项目内组织

当前以 `docs/策划案.md` 作为稳定入口，以 `docs/gdd/index.md` 作为设计状态与事实源索引。
只维护已有内容需要的领域文件，不为形式创建空文件：

```text
docs/gdd/
├── index.md                  # 文档入口、当前版本和各领域事实源
├── product-and-pillars.md    # 产品摘要、目标体验和设计支柱
├── core-loop.md              # 局内、局外循环及阶段衔接
├── food-and-upgrades.md      # 食材基线、普通强化和特殊构筑
├── combat.md                 # 餐车耐久、食客、精英和 Boss
├── progression-and-levels.md # 关卡范围、内容解锁和局外成长
├── presentation.md           # 界面层级、反馈、画面和声音方向
├── validation-and-scope.md   # 原型验证问题、记录数据和制作边界
├── open-questions.md         # 候选、冲突待裁决和待验证问题
└── decision-log.md           # 已确认修改、替代和废弃历史
```

- 每条完整规则只指定一个现行事实源；其他文档使用摘要和链接，不复制整套规则。
- `docs/策划案.md` 只提供稳定入口；`docs/gdd/index.md` 维护状态总览并链接到各领域唯一事实源。
- JSON、Excel 和 `.tres` 等结构化数据负责精确字段或数值；GDD 负责解释语义、边界和体验目的。
- 不把开发日志改造成现行 GDD；日志只保存当时的实现与问题证据。

## 完成状态

- `已确认`：用户明确确认，或资料中为无冲突的现行设计。
- `待验证`：方向明确但需要原型、模拟或试玩证据。
- `候选`：尚未确认的建议或灵感。
- `冲突待裁决`：存在不能同时成立的来源。
- `已废弃`：有明确替代或废弃证据。

## 决议后的维护规则

用户明确确认设计决议后：

1. 更新对应现行章节，使读者不依赖聊天记录也能理解完整规则。
2. 删除或改写已被替代的现行表述，避免互相矛盾的版本同时存在。
3. 在 `decision-log.md` 追加决策日期、主题、确认结果、替代或废弃内容、理由、影响文档和确认来源。
4. 在 `open-questions.md` 移除已经解决的问题；新出现但未解决的问题写回并标明阻塞范围。
5. 更新 `docs/gdd/index.md` 中的状态、摘要、冲突项和事实源定位；路径或标题变化时修复受影响链接。
6. 只有用户明确决定废弃时才把设计标记为 `已废弃`。废弃意味着不再指导当前实现，但仍在决策记录中可追溯。
7. 删除整份资料前先确认其中没有仍有效的唯一信息；有历史价值时移至 `docs/archive/`，并在索引中说明替代来源。

决策记录使用以下最小格式：

```text
日期：
主题：
状态：已确认 / 已替代 / 已废弃
最终决定：
替代或删除的旧内容：
决策理由：
保留的原始意图：
影响范围：
确认来源：当前对话 / 指定资料
```

## 系统规格最小字段

```text

关联设计支柱：
玩家输入：
系统状态：
核心规则与优先级：
输出与反馈：
成功、失败和中止：
数据与事件：
依赖系统：
边界与降级行为：
来源与状态：

```

不确定时保留空缺和问题，不替用户补成事实。
