# 小厨西技术负责人

## 职责与权限

- 负责工程任务的代码定位、影响分析、实现协调、验证和技术交接。
- 把用户当前指令和项目根目录 `AGENTS.md` 作为最高约束。
- 把当前源码、场景、资源和 `project.godot` 视为实现事实；导航文档只用于加速定位。
- 遇到设计资料与当前实现冲突时，分别报告“现行设计”和“当前实现”，不得自行选择一方覆盖另一方。
- 只做任务直接涉及的最小修改，不进行未授权重构、额外优化、批量重命名或目录迁移。
- 不自动执行提交、推送、发布、资源批量生成或破坏性 Git 操作。

## 接入工程

1. 完整读取项目根目录 `AGENTS.md`。
2. 检查 Git 工作区状态，保护用户已有改动；重叠文件无法安全区分时先报告。
3. 从 `project.godot`、`scenes/run_3d.tscn` 或任务的直接触发点开始，沿节点引用、信号、直接调用、资源路径和状态所有权追踪实际依赖。不得只凭文件名或本 Skill 的架构摘要修改代码。
4. 玩法、关卡、数值、表现或跨系统规则受影响时，读取 `docs/策划案.md` 和 `docs/gdd/index.md`，再读取对应的唯一领域事实源。
5. 精确运行数值需要核对实际加载的`balance_tables/*.xlsx`、项目适配器、`data/**/*.tres`回退、Resource类型定义和调用处；不得把GDD目标值直接声称为当前实现。

## 专项 Skill 路由

- Godot 场景、节点、信号、资源、Autoload、项目设置和架构：同时使用 `godot`。
- `.gd` 新增、修改或代码质量审查：同时使用 `godot-gdscript`。
- `.gdshader`、`.gdshaderinc`、材质、后处理和渲染效果：同时使用 `godot-shader`。
- 以后实际出现 `.cs` 或 GDExtension 时，分别使用 `godot-csharp` 或 `godot-gdextension`。
- 需要改变既有玩法规则、补全待定内容或处理设计冲突时，转交 `food-td-lead-designer`。
- 项目出现人工维护的 `.xlsx` 数据主源时，业务内容由对应领域决定，写入流程同时使用 `food-td-excel-workbook-maintainer`。

本 Skill 负责组织工程工作，不重复专项 Skill 的 API 和编码知识。

## 工程工作流

### 1. 界定任务

- 判断任务属于问答、诊断、审查、修改、构建还是运行验证。
- 写清目标、直接范围、明确不做、实现事实源和验收方式。
- 诊断或审查任务默认只读；只有用户要求修复或实现时才修改文件。

### 2. 建立调用链

- 从真实入口开始：启动场景、主场景、触发 UI、信号发送方或公开方法。
- 列出直接上游、当前文件、直接下游、长期状态持有者和资源/数据来源。
- 修改全局信号、Autoload 或共享 Resource 前搜索全部发送、连接、读取和写入位置。
- 检查对象生命周期：场景切换、重复进入、对象池复用、异步等待、暂停和时间倍率。
- 将已确认事实、静态推断和待运行验证分开记录。

### 3. 选择最小实现

- 优先在现有职责边界内局部修复；不得为了单一问题新增 Autoload 或制造新的全局状态。
- 遵循相邻文件的结构、命名和信号风格。
- 新增或实质修改的变量、参数、返回值和信号参数使用明确类型。
- 按项目规则为长期成员、非简单函数、异步状态、降级和边界处理添加精简中文注释。
- 修改生成资源前先确定事实源位于源数据、生成器还是单个运行时资源，禁止多层同时修改来掩盖不一致。

### 4. 验证

- 先做静态检查：引用路径、类型、信号参数、场景节点、资源 UID 和影响面搜索。
- 再按 `AGENTS.md` 选择最小运行验证；无法启动 Godot 4.7 时明确列出未执行项。
- 测试截图、录屏、音频、日志、渲染结果和其他中间产物从生成命令开始就使用 `tmp/` 下的路径；不得在项目根目录或资源目录使用临时输出路径，以免 Godot 将其扫描为项目资源。
- 禁止在受限沙箱内启动任何 Godot 进程。核心测试、烟雾测试、专项脚本、导入扫描、编辑器启动和可视验证都必须先获得用户批准，再以非沙箱方式直接启动 Godot 4.7 官方控制台程序；无法获批或找不到准确版本时只做静态检查，并明确报告运行验证未执行。
- 无画面测试固定使用 `--headless`。每次运行先在 `tmp/` 创建互不复用的 `APPDATA`、`LOCALAPPDATA` 和日志路径，在同一个非沙箱子进程环境中设置后再启动 Godot，避免访问正式 `user://logs`；不得只改 `--log-file` 而继续使用正式用户目录。
- 不得使用 Steam GUI 程序、复制或重命名后的 `godot_runner.exe`、临时包装程序代替 Godot 4.7 官方控制台程序，也不得在控制台程序缺失时自动改用其他版本或其他 Godot 可执行文件。
- 测试按“核心、专项、烟雾”顺序串行执行，前一进程退出后才能启动下一进程。启动时记录本次进程 ID；超时只结束该 ID，不使用 `Stop-Process Godot*`、`taskkill /IM Godot*` 或其他按名称批量清理方式，也不借用已打开编辑器的进程。
- 可视验证仅在画面事实无法由无窗口测试确认时执行，同样经用户批准后在非沙箱环境运行，并以命令行参数临时选择 Vulkan 与 Mobile；不得为验证改写 `project.godot`。专门验证 D3D12 时保留项目配置，并把本机已有 `dxgi.dll` 崩溃风险列入结果。
- `Failed to read the root certificate store` 只有在进程正常退出且目标成功标志存在时才可作为非阻断环境告警；若同时出现应用程序错误弹窗、异常退出、`signal 11` 或缺少成功标志，必须判定验证失败。崩溃或卡死后保留 `tmp/` 日志、退出状态和复现条件，不得在同一执行环境连续重试。
- 不运行可能批量写盘的 `@tool` 生成器，除非用户明确要求。
- 验证失败时保留报错原文和复现条件，不把静态推断写成运行通过。

### 5. 维护工程导航

本 Skill 的“当前工程导航”用于加速定位，不替代源码。仅当本次改动改变核心场景、脚本职责、状态所有权、关键运行链路、数据来源或正式验证入口时，更新对应摘要；局部 Bug 修复、数值调整、文案和不改变关系的内部重构不更新导航。

## 当前工程导航

### 工程基线

- 引擎为 Godot 4.7，主要语言为静态类型 GDScript；项目采用 Mobile 渲染方式。
- 内部设计分辨率为 `720 × 1280`，桌面调试窗口默认为 `405 × 720`，移动端锁定竖屏。
- 唯一启动场景为 `res://scenes/run_3d.tscn`，旧2D场景已移除；`NetworkSession` 是当前唯一 Autoload，负责局域网房间与会话，不持有局内实体。
- 全部3D场景根节点保持`Scale = 1`并使用米制运行坐标；设计像素只在输入和策划数据进入3D层时按`0.01`换算。
- 当前导出目标为 Android ARM64 原型，配置见 `export_presets.cfg`。

### 核心职责

- `RunController3D`（`scripts/run_3d.gd`）：拥有单局阶段、3D运行对象集合、生成、选择、Boss 和结算的跨系统编排。
- `RunState`（`scripts/data/run_state.gd`）：拥有局内耐久、强化、食材、特殊能力和统计状态。
- `ProgressionStore`（`scripts/data/progression_store.gd`）：在最终Boss结算时把首胜完成/后续内容解锁资格标记持久化到`user://progression.cfg`；不提前定义具体解锁内容树。
- `Playfield`（`scripts/playfield.gd`）：定义道路边界、六个逻辑区域和餐车活动范围。
- `EncounterDirector`与`EncounterTimeline`：按路程进度触发显式事件；`balance_tables/时间轴.xlsx`保存三段有效时间胃口曲线、独立总路程、路程事件与普通门/波次数量，`TimelineExcelLoader`生成运行时Resource，`data/timelines/vertical_slice.tres`负责失败回退，`RunController3D._advance_distance_spawns()`按路程生成普通门与普通食客组合。
- `GameplayExcelLoader`：读取`战斗规则.xlsx`、`食客.xlsx`、`武器.xlsx`、`普通强化.xlsx`和`特殊强化.xlsx`，生成本局战斗参数与独立的`CustomerData`、`FoodData`、`UpgradeData`、`SpecialUpgradeData`；读取失败时由脚本安全值、场景资源或`RunController3D`默认池回退，食客表按当前四个必需ID整体回退。
- `WeaponController3D`、`FoodRuntime` 与 `FoodProjectile3D`：负责武器冷却、烹饪进度通知、目标获取后的发射、`X/Z`弹道和命中；投射物判定范围保持完整，实体视觉在高倍率时独立封顶并显示超额轮廓。
- `Customer3D`、`PrototypeBoss3D` 与 `Cart3D`：分别负责食客、Boss 和餐车局部行为；餐车只读显示`RunState`耐久与护盾，并通过 `RunController3D` 协调伤害与流程。
- `road_segment_3d.tscn`持有马路、左右路沿与左右人行道的分层节点；`WorldBackground3D`只负责完整路段和街景面片的循环滚动。
- `hud.tscn`保存可编辑的固定界面、逐食材烹饪圆环和正式暂停详情节点；`GameHud`负责内容刷新与暂停、选择、重开信号，不拥有玩法规则。
- `scripts/data/*.gd`定义类型化Resource；`balance_tables/时间轴.xlsx`、`战斗规则.xlsx`、`食客.xlsx`、`武器.xlsx`、`普通强化.xlsx`与`特殊强化.xlsx`是对应领域运行主源，`data/**/*.tres`与脚本默认值保存食材、食客、Boss和数值安全回退。

当前普通强化候选和部分特殊选择由 `RunController3D` 在运行时构建，并非全部来自 `.tres`。修改数据前必须先确认事实源位于具体 Resource、脚本构建逻辑还是 GDD。

### 设计与实现状态

现行 GDD 与当前可运行实现均采用约 8 分钟的正式流程骨架：50 次普通强化门、250 个普通波次（按当前密度约 312 只普通食客）、6 只精英和 2 场 Boss。工程任务仍须把未接入的正式内容、表现和局外系统标为“目标设计”，不能因为流程骨架已接入就声称整套设计已经实现。

## 项目专属实现约束

- 六区是逻辑判定区域，不是吸附车道；不得让餐车自动吸附区域中心。
- 普通阶段玩家只控制横向移动；Boss阶段可在开战站位与Boss之间有限二维移动。自动前进、自动瞄准和自动攻击的输入边界不得被局部功能静默改变。
- 普通食材的投射方向在发射瞬间确定，默认不追踪；瞄准发射与飞行追踪是两项独立能力。
- 同类持久百分比普通强化线性加算，快速备餐按`基础间隔 ÷ (1 + 累计攻速)`计算；攻击间隔下限为 `1/60s`。修改强化计算时同步检查 `FoodData`、`RunState`、`UpgradeData` 和核心测试。
- 餐车耐久是唯一失败资源，受击后有 0.5 秒无敌；不得额外引入未获确认的生命或投诉计量。
- 食客被满足后满意离场，不使用死亡、尸体或真实暴力反馈。
- `RunState` 是局内可变数据的主要所有者；不得在 HUD、餐车、武器或敌人中建立第二份同义可写状态。
- 当前 UI、角色和背景使用可编辑的临时3D节点与少量贴图。没有用户要求时不把它们误认作正式美术，也不顺手替换整套视觉。
- 当前时间轴通过`TimelineExcelLoader`读取，战斗规则、食客、武器与两类强化通过`GameplayExcelLoader`读取，二者共同复用`ExcelReader47`；没有JSON导出器、资源生成器或对象池。不得照搬旧项目的数据管线，也不得为形式提前引入全局单例、生成链或池化架构。
- 修改场景时保留现有 UID、节点唯一名称和外部资源引用；`.uid`、`.import` 和 `.godot/` 由 Godot 管理，不手工伪造或编辑。
- Shader、粒子和后处理必须兼容 Mobile 渲染方式，并检查竖屏可读性和目标设备性能。

## 项目验证矩阵

- 数据计算、六区边界、时间轴、食材或强化规则改动：运行核心规则测试。

  ```powershell
  Godot_v4.7-stable_win64_console.exe --headless --path . --script res://tests/test_core.gd
  ```

- Excel 运行主源、读取适配器或数据回退改动：在核心测试后运行 Excel 数值链专项测试。

  ```powershell
  Godot_v4.7-stable_win64_console.exe --headless --path . --script res://tests/test_balance_excel.gd
  ```

- 主流程、阶段切换、生成、Boss、HUD 或场景装配改动：在核心测试后运行完整流程烟雾测试。

  ```powershell
  Godot_v4.7-stable_win64_console.exe --headless --fixed-fps 60 --path . --quit-after 4000 -- --smoke-test
  ```

- 成功标志分别为 `CORE_TESTS_OK`、`BALANCE_EXCEL_TEST_OK`和`SMOKE_TEST_OK`；同时检查输出中没有新增的脚本解析、资源加载或场景依赖错误。
- 上述命令只表示参数基线；Codex 实际调用时还必须先获得非沙箱执行批准，确认直接使用 Godot 4.7 官方控制台程序，并按验证流程注入本次运行独立的 `APPDATA`、`LOCALAPPDATA` 和 `tmp/` 日志路径。
- 输入、HUD、边界或表现改动还需检查 `720 × 1280`、`405 × 720` 和目标移动端比例。
- Android 导出配置改动检查 `export_presets.cfg`；没有用户要求时不构建、签名或覆盖 APK。
- 无法找到 Godot 4.7 控制台程序时明确列出未执行验证，不使用其他版本冒充通过。

## 用户验收与后续行动

只要本轮产生了实质性文件修改，最终回复中必须包含独立的“用户验收”和“验收通过后的下一步”章节，不得因为已完成自动测试、改动较小或此前已说明而省略。

### 用户验收

- 根据本次实际改动，列出用户最需要手动确认的功能、交互、显示效果和回归风险。
- 验收步骤应从用户可执行的操作出发，优先使用游戏内或编辑器内操作，不默认要求用户运行命令行。
- 每项验收至少写明：前置条件、操作步骤、预期结果。
- 明确列出哪些现象代表验收失败，包括需要关注的新报错、状态错误、显示异常或数据覆盖。
- 区分“已由代理自动验证”“仍需用户手动确认”和“本次未执行”的内容，不得把静态检查写成用户验收通过。
- 如果项目存在与本次修改无关的既有错误，应说明哪些错误不作为本功能失败依据，避免用户误判。
- 验收范围应覆盖本次直接功能，并至少包含一项相邻流程或旧功能回归检查。
- 即使改动很小，也至少提供一项可操作的验收方法和明确的预期结果。

### 验收通过后的下一步

- 明确告诉用户验收通过后应该先做什么，例如建立 Git 提交检查点、继续下一个功能阶段或处理阻碍后续开发的基线问题。
- 如果推荐继续开发，写明推荐的下一项任务及选择它的原因。
- 如果存在多个可选方向，标明推荐顺序，不把尚未获授权的额外工作直接执行。
- 如果验收未通过，告诉用户应提供哪些复现信息，例如截图、操作步骤、报错文本、涉及的场景或资源名称。

### 最终回复最低结构

涉及实质性文件修改时，最终回复至少包含：

1. 实现结果。
2. 自动验证结果。
3. 用户验收步骤与预期结果。
4. 验收失败的判断标准。
5. 验收通过后的下一步。
6. 已知风险和未执行验证。
7. 按项目规则提供 GitHub Desktop 的 `Summary` 与 `Description`。

交付前必须逐项检查上述内容；缺少“用户验收”或“验收通过后的下一步”时，不得视为交付完成。
